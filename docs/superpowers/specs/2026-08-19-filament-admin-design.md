# Bandingin — Filament Admin Panel (Part 2 of 3)

**Date:** 2026-08-19
**Status:** Approved
**Scope:** Install Filament and build resources over the Part 1 schema. Part 1 (database) is merged; Part 3 (wiring the Livewire frontend to Eloquent) is a separate spec.

## Context

Part 1 moved the catalogue into 14 database tables with models, factories and seeders, while leaving the public site running on the hardcoded `App\Support\*` classes. Nothing can edit that data yet — this part supplies the admin surface.

### Version compatibility (verified, not assumed)

This project runs **Laravel 13.25** and **Livewire 4.4** on **PHP 8.4**. Filament v4 targets Livewire 3, so it is the wrong line here. **Filament v5** exists specifically to add Livewire v4 support and is otherwise functionally identical to v4; new features ship to both majors.

`composer require filament/filament:"^5.0" --dry-run` resolves cleanly to **v5.7.6** against the current lock file with no conflicts. Pin `^5.0`.

### Decisions made during brainstorming

1. **Access** — login only, registration disabled. Any `users` row may sign in. No `is_admin` column and no permissions package: there is exactly one role today.
2. **Account creation** — no custom command. Filament ships `php artisan make:filament-user`, which covers this with no code to write; `php artisan tinker` remains available for scripted cases.
3. **Phone editing** — the 19 specs render inline on the phone form (they always all exist); variants and listings are relation managers (variable count, independently edited).
4. **Scope** — all 11 resources in this part.
5. **Article comparison block** — a RichEditor custom block storing two phone IDs, rendered from live phone data so it cannot go stale.
6. **Dashboard** — one stats widget plus a latest-reports table. No charts.
7. **Reports** — gain a nullable `status` enum column for triage.

## Panel

A single panel at `/admin`, registered by `app/Providers/Filament/AdminPanelProvider.php` (generated by `php artisan filament:install --panels`).

- `->login()`, and **no** `->registration()` — accounts are created manually.
- `->brandName('Bandingin')`.
- Sidebar navigation groups: **Katalog**, **Konten**, **Operasional**.
- `User` implements nothing extra; every user row is an admin. When a second role appears, introduce `FilamentUser::canAccessPanel()` then — not now.

Creating the first account uses Filament's own command — no project code required:

```bash
php artisan make:filament-user
```

## PhoneResource in detail

The main form, in sections:

1. **Identitas** — brand select, name, slug, price, tag, `published_at`.
2. **Bodi & jaringan** — nfc toggle, ip68 toggle, dimensions, network, `released_label`, `released_at`.
3. **Skor** — the five 0–100 score fields.
4. **Plus & minus** — pros and cons repeaters (simple string lists).
5. **Spesifikasi** — all 19 specs inline, rendered as a repeater over the `specs` relation, ordered by `spec_definitions.sort` and visually grouped by `spec_definitions.group`. Each row shows the definition label (read-only), `display_value`, and `comparable_value`.

`comparable_value` carries a permanent helper text stating the project rule: **higher always wins, so inverted metrics are stored negated** (198 g is entered as `-198`). Getting this wrong makes the duel pick the wrong winner, and the field looks innocuous without the warning.

Relation managers as tabs:

- **Variants** — label, price, `is_default`, sort. Reorderable.
- **Listings** — store, price, product URL, note, warranty tag, plus a read-only snapshot count column. Editing a price here writes a `price_snapshots` row automatically via the existing `PhoneListingObserver`; no admin code touches snapshots.

The table lists slug, name, brand, price, cheapest listing (computed via `min('price')` over the listings relation, never stored), published state. Filters: brand, published/draft, has-NFC, IP68.

**N+1 discipline:** every table that shows a related value eager-loads it (`->modifyQueryUsing(fn ($query) => $query->with('brand'))`, `withCount('listings')`, and so on). This is a project rule, not a nicety.

## Article comparison block

`app/Filament/RichContent/PhoneComparisonBlock.php`, extending `Filament\Forms\Components\RichEditor\RichContentCustomBlock` (generated by `php artisan make:filament-rich-content-custom-block PhoneComparisonBlock`).

- `getId()` → `phone_comparison`; `getLabel()` → `Tabel perbandingan`.
- `configureEditorAction()` — two searchable phone selects and a multi-select of spec keys to display (defaulting to the summary row set).
- `toPreviewHtml()` — a compact editor preview naming both phones.
- `toHtml()` — renders the full table from **live** phone data, so prices and specs never drift from the catalogue.

Storage stays **HTML** (Filament's default), which keeps Part 1's `longText` body column and its seeded plain-HTML bodies valid — a seeded body containing no blocks passes through the renderer unchanged. Part 3 renders article bodies through `RichContentRenderer` so blocks expand; that is noted here as a Part 3 dependency, not built now.

## Report status

One migration adds a nullable `status` string column to `reports`, backed by a new `App\Enums\ReportStatus` (`Baru`, `Diproses`, `Selesai`, `Ditolak`). Nullable and unread by the frontend, so `/lapor` and its existing tests are unaffected. `Report` gains the cast; `ReportFactory` gains a state.

## Dashboard

`CatalogStatsWidget` — four stats: published phones, brands, reports awaiting triage (`status` null or `Baru`), newsletter subscribers.

`LatestReportsWidget` — the five newest reports as a table, linking to the report resource.

No charts. `price_snapshots` currently holds exactly one row per listing, so any trend line would render flat and imply the tracker exists when it does not.

## Testing

Pest feature tests under `tests/Feature/Filament/`:

- The panel redirects guests to login; an authenticated user reaches the dashboard.
- Each resource's list page renders for an authenticated user (a dataset over the 11 resource classes keeps this to one test).
- Creating a phone through the form persists it with its specs attached.
- Editing a listing's price through the relation manager writes a new `price_snapshots` row.
- The report status filter narrows results, and the status action updates a report.
- An `arch` test asserting no class under `app/Filament/**` is referenced from `app/Livewire/**`, enforcing the Part 2/Part 3 boundary mechanically.

## Out of scope

- **Any change to `app/Livewire/`, `app/Support/`, `app/Data/`, or `resources/views/`.** The public site keeps rendering from the Support catalogues until Part 3. The arch test enforces this.
- Image and media uploads — no image columns exist in the schema yet.
- Roles, permissions, activity logging, multi-language, and soft deletes.
- Price-tracking jobs or any scraper.
